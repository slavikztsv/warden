# P2·A6 — Taking the Broker Off the Event Loop: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the broker's one-tool-call-at-a-time ceiling by making the
audit append constant-time (B1) and running the synchronous spine on a
threadpool the broker owns (A6), without changing a single interface.

**Architecture:** `AuditLog` caches its chain head on the first append instead
of re-parsing the whole log on every one. The broker constructs one
`ThreadPoolExecutor`, sized by config, and every place that called the spine or
`authorize_connect` inline now awaits it through that executor. The spine, the
PDP, the adapters and `TaskStateStore` all stay synchronous.

**Tech Stack:** Python 3.12, FastAPI/Starlette, `concurrent.futures.ThreadPoolExecutor`,
`asyncio.get_running_loop().run_in_executor`, OPA/Rego, pytest, `ruff`, `mypy`.

**Spec:** [2026-08-06-p2a6-taking-the-broker-off-the-loop-design.md](../specs/2026-08-06-p2a6-taking-the-broker-off-the-loop-design.md)

  is green at every commit.
- **The gate is all four, before every commit:**

- **The `.venv` cannot be recreated.** Use it; do not rebuild it. No new runtime
  dependency is needed by this plan — `concurrent.futures` and `asyncio` are stdlib.
- **A green suite is not evidence.** Every property below names a mutation that
  must turn its test red. Apply the mutation, watch it fail, restore with
  `git checkout --`, confirm `git status` is clean. Record the result in the
  commit message.
- **No `sleep` in tests, and no timing assertions.** "Does not re-read" is
  asserted as a call count; "runs off the loop thread" as a thread identity.
- **`tests/golden/audit-4711.jsonl` is never regenerated by this plan.** No
  policy input changes, so the frozen chain stays frozen.
- **Do not add `executor` to `BrokerComponents.as_app_kwargs()` or

  which is keyword-only with no `**kwargs`; a new key there raises `TypeError`
  inside *every* `CONNECT`, at request time, with the broker still reporting
  healthy. `wiring.py`'s module docstring records that exact incident.

```python
def test_appending_does_not_re_read_the_log(tmp_path):
    """B1. `_head()` used to read and JSON-parse the WHOLE file on every
    append -- inside the lock, which is what every concurrent caller queues
    on. Measured before the change: 0.76ms per append at 100 records, 8.0ms
    at 1000, 37.1ms at 4000, and 71.8s for 4000 appends.

    Asserted as a call count, not a duration: the property is "does not
    read", and a timing assertion would be flaky as well as weaker.

    The FIRST append is allowed one read -- that is where the cache is
    populated, and it is once per process. Every append after it must read
    nothing.
    """
    log = AuditLog(tmp_path / "audit.jsonl")
    _append(log)  # populates the cache

    reads = []
    real_records = log.records

    def counting_records():
        reads.append(1)
        return real_records()

    log.records = counting_records  # instance attribute shadows the method
    for _ in range(5):
        _append(log)

    assert reads == [], f"append re-read the log {len(reads)} times"
    del log.records
    assert log.verify_chain() == (True, None)
    assert [r["seq"] for r in log.records()] == [1, 2, 3, 4, 5, 6]


def test_a_failed_write_does_not_advance_the_cached_head(tmp_path):
    """The cache is advanced AFTER the write returns, never before.

    Advancing first would leave it one record ahead of the file, and the
    chain would break at the NEXT successful append -- a corruption one call
    removed from the thing that caused it, which is the hardest kind to
    diagnose from the artifact this system exists to produce.
    """
    path = tmp_path / "audit.jsonl"
    log = AuditLog(path)
    first = _append(log)

    with patch.object(Path, "open", side_effect=OSError("disk full")):
        with pytest.raises(OSError):
            _append(log)

    second = _append(log)
    assert second["seq"] == 2, "the failed write consumed a sequence number"
    assert second["prev_hash"] == first["hash"]
    assert log.verify_chain() == (True, None)
    assert AuditLog(path).verify_chain() == (True, None)
```

```python
        #
        # Populated LAZILY, on first append, and deliberately not in this
        # constructor. `warden verify-chain` exists to be pointed at a
        # CORRUPT log and report "chain BROKEN: malformed record" -- and

        # anyway. The win was never the first append; it was the
        # four-thousandth, where re-parsing the whole log cost 37ms inside
        # the lock every concurrent caller queues on.
```

Replace the body of `_head` so it consults the cache:

```python
    def _head(self) -> tuple[int, str]:
        """The (seq, hash) the next record links to.

        Only ever called from `append`, under the lock -- so the first-append
        read cannot race a concurrent second append.
        """
        if self._head_cache is None:
            existing = self.records()
            self._head_cache = (
                (existing[-1]["seq"], existing[-1]["hash"])
                if existing
                else (0, GENESIS_HASH)
            )
        return self._head_cache
```

Then, in `append`, advance the cache after the write and before the return.
The `with self.path.open(...)` block is unchanged; add the assignment
immediately after it, still inside `with self._lock:`:

```python
            # AFTER the write returns, never before: if it raised, the cache
            # still describes what is actually on disk, so the next append
            # computes from the true head rather than from a record that was
            # never written.
            self._head_cache = (record["seq"], record["hash"])
            return record
```

```python
        # the store's atomic charge, not by this call being inline (see
```
